IVL — Design Document

IVL Match Prediction

Design Document  ·  Last updated June 2026

Overview

This project collects historical match data from IVL (Identity V League) official Bilibili posts, identifies the MVP player from each match image, and builds a structured dataset for future match prediction.

The pipeline has two stages: automated data collection and semi-supervised MVP labeling.

Problem Statement

IVL match results are published as Bilibili posts containing two images — a scoreboard and an MVP card. There is no official API or structured data source. The MVP player name appears as stylized game-UI text in the image, which standard OCR handles poorly due to the condensed bold font.

Components

data_collection.py

Scrapes the IVL official Bilibili account using Playwright (headless Chromium). Intercepts API responses from opus/feed/space to collect post metadata, then opens each post page to extract real image URLs from HTML.

FunctionDescription
detect_season(text)Regex-matches Chinese season strings, returns English name e.g. 2025IVL_Autumn_Finals. Covers both Finals and Regular Season.
extract_teams(text)Parses TeamA vs TeamB from post text, strips Chinese characters
extract_winner(text)Finds #Team获胜 pattern
calc_match_score(text)Parses individual game scores e.g. 5:3, computes overall win-loss
extract_image_urls_from_html(page)Extracts hdslb.com image URLs directly from page HTML
download_image(url, path)Downloads image with timeout

result_images/

              ├── score_3-1.png
              └── mvp.png           ← name unknown, filled later

CSV columns: match_id, team_a, team_b, date, winner, match_score, game_scores, mvp

The mvp column is left empty at this stage and filled by clip_label.py after labeling.

CSVs are saved to csv_output/, one file per season (e.g. 2025IVL_Autumn_Finals.csv).

clip_label.py

Identifies MVP players from mvp.png images using CLIP embeddings and KMeans clustering, with human correction and automatic CSV update.

Why CLIP instead of raw OCR: Standard OCR fails on the game's condensed bold UI font. CLIP encodes images into a semantic embedding space where visually similar images — two cards showing the same player — cluster together regardless of background variation.

Pipeline:

mvp.png images (unlabeled only — already-labeled mvp_*.png are skipped)
    │
    ▼
get_ticket()          HSV mask → find ticket region → crop & resize
    │
    ▼
embed_tickets()       CLIP ViT-B/32 → 512-dim embeddings → L2 normalize
    │
    ▼
PCA(50 dims, seed=42) → KMeans(k=40, seed=42)
    │
    ▼
ocr_ticket()          Tesseract on cluster representative → suggest name
    │
    ▼
cluster_labels_clip.csv   ← human corrects wrong suggestions
    │
    ▼
apply_labels()        rename mvp.png → mvp_{player}.png
    │
    ▼
_update_csv_mvp()     scan filenames → write mvp column to csv_output/*.csv

Commands:

# Step 2: open cluster_sheet_clip.png, fix wrong names in cluster_labels_clip.csv

Design Decisions

Why Bilibili scraping instead of an API?

IVL has no public data API. The official account posts structured match result images consistently, making it a reliable source.

Why CLIP for MVP identification?

The MVP player name appears as stylized game text that standard OCR cannot reliably read. CLIP embeds images semantically — the same player's card looks similar across matches regardless of background scene. KMeans clustering groups same-player cards together, requiring only one human correction per cluster rather than per image.

Why semi-supervised instead of fully automated?

Background variation in the game causes some same-player cards to split into different clusters. A fully automated approach would require a labeled training set that doesn't exist. The semi-supervised approach (cluster → human label → apply) achieves high accuracy with minimal manual effort (~40 corrections for ~200 images).

Why separate data collection from labeling?

Scraping is slow (requires browser automation) and labeling benefits from reviewing all images at once. Separating the two stages allows each to be re-run independently. Already-labeled images (mvp_*.png) are skipped on subsequent --build runs, so only new images need to be reviewed.

Why split CSV by season?

Regular season and Finals matches have different formats and analytical relevance. Splitting into separate files makes downstream analysis cleaner, and matches the naming of the existing dataset.

Known Limitations

  • Background scene variation can split the same player into 2–3 clusters, requiring manual merge in cluster_labels_clip.csv.
  • The date column in CSV is currently empty — Bilibili's API response format for timestamps varies.
  • Season detection covers 夏季赛, 秋季赛 (Regular + Finals). Other season formats would need additional patterns in detect_season().

项目概述

本项目从 IVL（第五人格联赛）官方 Bilibili 账号收集历史赛事数据，从每场比赛的图片中识别 MVP 选手，构建结构化数据集，用于未来的赛事预测。

整个流程分为两个阶段：自动化数据采集 和 半监督 MVP 标注。

问题背景

IVL 赛果以 Bilibili 动态的形式发布，每条动态包含两张图片——比分图和 MVP 图。官方没有提供任何 API 或结构化数据源。MVP 选手名字以游戏 UI 风格的特殊字体出现在图片中，标准 OCR 由于字体为压缩粗体，识别效果很差。

设计决策

为什么爬 Bilibili 而不是用 API？

IVL 没有公开的数据 API。官方账号固定格式发布赛果动态，是可靠的数据来源。

为什么用 CLIP 识别 MVP？

MVP 选手名以游戏特殊字体显示，标准 OCR 无法可靠识别。CLIP 对图片进行语义编码——同一选手的票据图在不同比赛背景下仍会聚在一起。KMeans 将同一选手的图片归为一个 cluster，只需人工校正一次即可，不需要逐图处理。

为什么用半监督而不是全自动？

游戏背景变化会导致同一选手的图片被分到不同的 cluster。全自动方案需要已标注的训练集，目前不存在。半监督方案（聚类 → 人工标注 → 应用）在约 200 张图片中只需约 40 次人工修正，效率高且准确。

为什么把数据采集和标注分开？

爬取速度慢（需要浏览器自动化），而标注最好在所有图片都下载后统一进行。分离两个阶段可以独立重跑。已标注的图片（mvp_*.png）在下次 --build 时自动跳过，只有新图片需要人工处理。

为什么按赛季分 CSV？

常规赛和总决赛的赛制和分析意义不同。分文件存储让后续分析更清晰，也与现有数据集的命名保持一致。
