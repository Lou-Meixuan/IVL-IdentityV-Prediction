# IVL 冠军预测 —— 设计文档 (Prediction Design Doc)

> 目标读者:本项目作者(你)。这份文档回答一个问题:**手里这些 metadata,要怎么一步步变成"谁会夺冠"的预测?**
> 配套已有文档:`docs/design.html`(数据采集 pipeline 设计)。本文档承接其后,只讲**预测建模**部分。
> 状态:v0.1 草案,待你确认后细化。

---

## 0. 一句话结论(先看这个)

直接预测"冠军是谁"几乎训练不出来(每个赛季只有 1 个冠军,历史样本个位数)。**正确做法是:先训练一个"单场比赛胜率"模型(数据量大、可验证),再用蒙特卡洛模拟把整个季后赛打几万遍,统计每支队伍夺冠的次数 → 得到夺冠概率。** 这也是 FiveThirtyEight 等体育预测的标准套路。

下面把两条路线都摊开对比,再给出数据、特征、模型、验证和落地路线图。

---

## 1. 问题定义

### 1.1 你真正想要的输出

一个表格,长这样:

| 战队 | 夺冠概率 |
|------|---------|
| MRC  | 34% |
| Gr   | 25% |
| TE   | 18% |
| …    | … |

而不是一个硬邦邦的"冠军 = MRC"。概率化输出才能验证好坏、才有信息量。

### 1.2 为什么不能"直接预测冠军"

把"谁是冠军"当成一个分类标签直接学,会遇到三个致命问题:

1. **样本极少**:目前你有 2025夏、2025秋 两个完整赛季 + 2026夏(进行中)。也就是说"冠军"这个标签历史上只出现过 2~3 次。任何模型都没法从 3 个样本里学到规律。
2. **标签泄漏风险高**:冠军和"赛季总胜场""总比分"高度相关,模型很容易学成"谁赢得多谁是冠军",等于没预测。
3. **无法回测**:只有 2~3 个历史冠军,没法做交叉验证,你永远不知道模型到底准不准。

### 1.3 重新拆解目标(关键转换)

把"夺冠"拆成它的**组成部分**——一连串单场对局:

```
夺冠概率  =  在季后赛 bracket 里赢下每一轮的概率连乘
          =  f(每一场 BO 的胜率)
单场 BO 胜率  =  g(两队的实力特征)
```

于是问题变成两个可学习的子问题:

- **子问题 A(核心)**:给定 A 队 vs B 队,预测 A 赢这场 BO 的概率 `P(A win)`。 → 数据多(每赛季 ~90 场),可严格验证。
- **子问题 B(模拟)**:有了任意两队的胜率函数,用蒙特卡洛把季后赛赛制跑 N 万次,统计夺冠频率。 → 纯计算,不需要训练。

**这就是全文的主线。**

## 2. 两条建模路线对比

你要求两条都写,这里完整对比,最后给推荐。

### 路线 A:单场胜率 + 蒙特卡洛模拟夺冠(推荐)

**流程**

1. 用历史对局训练 `P(A beats B)`。
2. 拿到当前赛季每队的实力评分/特征。
3. 按 IVL 实际赛制(常规赛积分 → 季后赛 bracket)模拟 N 万次。
4. 统计每队成为冠军的比例 = 夺冠概率。

**优点**

- 训练样本充足(对局级,每赛季近百场,跨赛季可累积到数百场)。
- 可严格验证:单场预测能用 Brier score / log loss 在历史数据上回测。
- 可解释:能输出"为什么看好这队"(评分高、近期状态好、克制对手等)。
- 增量友好:2026 赛季每打完一场,评分实时更新,夺冠概率随之刷新。

**缺点**

- 实现链条更长(要写模拟器,要懂赛制)。
- 模拟结果依赖单场模型质量,误差会传播。

### 路线 B:直接把"冠军"当标签预测

**流程**

1. 以"队伍 × 赛季"为一行样本,特征是该队赛季中段的统计(胜率、Elo、明星选手等)。
2. 标签 = 该队是否最终夺冠(0/1)。
3. 训练一个分类器输出夺冠概率。

**优点**

- 概念简单,一个模型直达目标,不用写模拟器。

**缺点(致命)**

- 样本量 = 赛季数 × 队伍数,但**正样本(冠军)只有赛季数那么多**(2~3 个)。严重不可学。
- 几乎无法验证(没有足够历史冠军做 CV)。
- 容易过拟合到偶然特征(某冠军恰好用了某英雄)。

### 推荐

**主线走路线 A。** 路线 B 可作为一个"健全性对照(sanity check)":在路线 A 模拟出夺冠概率后,可以用一个极简的 B 类逻辑(比如"赛季中段 Elo 最高的队最可能夺冠")做对比,看两者结论是否一致。但不要把 B 当成主模型。

> 一句话:**A 负责干活,B 只当参照物。**

## 3. 数据分层设计

你的工作数据集是 `IVL.xlsx`(5 个 sheet),天然分成三层。**先打通第一层,player 汇总层可顺手用,round 层最后补。**

> 注意:`IVL.xlsx` 和早期的 `csv_output/*.csv` 内容有重叠但不完全一致,`IVL.xlsx` 是更新、更"在整理中"的版本。以 xlsx 为准。

### 第 1 层:比赛级数据(核心,但需要先做整合)

这一层在 xlsx 里被拆成了**两张半成品表**,需要先合并:

- **`match_overview`(90 行)— 干净的赛程骨架,但结果几乎全空。** 优点是用了结构化 ID `2025SW1D1a`(= 2025 Summer · Week1 · Day1 · 第 a 场)并带 `date` 列,**天生按时间排序**,对 Elo / walk-forward 极其友好。缺点:`winner / match_score / mvp` 目前基本是空的(只填了 2 场)。覆盖 2025 夏季赛常规赛(W1–W10)。
- **`Sheet1`(198 行)— 爬来的结果,填得满,但 ID 乱、没日期。** 用 B 站数字 ID,`winner / match_score / game_scores / mvp` 都有,但**没有 date**,也没有结构化赛程位置。

**所以第 1 层的首要任务不是建模,而是"把 Sheet1 的结果填进 match_overview 的骨架里"**(整合方案见 §7 Phase 0)。整合完你就得到一张既干净、又按时间排好、结果完整的对局长表——这才是建模的真正输入。

### 第 1.5 层:选手赛季汇总数据(`COA_player_total_stats`,意外的捷径)

110 名选手的赛季汇总:`rank, player, round(场次), mvp_num, avg_performance_score, survivor_rounds, avg_kitting, avg_rescues, escape_rate, hunter_rounds, avg_eliminations, avg_knockdowns, avg_terror_shocks, four_kill_rate`。

**为什么重要:** 这是一条绕过 round 级 OCR 的**捷径**。本来"选手解码/救人/拉刀/淘汰"这类细节要靠逐局 OCR 才拿得到,但这张表已经把它们**按选手聚合好了**。把选手聚合回战队(按 `TEAM_player` 前缀),就能直接算出"战队阵容强度"特征(见 §4.1),无需等 round 数据。

**注意两个坑:**

- 这是**赛季汇总**(整季的平均值),不是逐场。它会**泄漏未来**(包含了赛季后期的表现)。所以**只能用于"赛季级/夺冠级"的粗特征,或严格切分的版本**,不能直接当作某场比赛的输入(详见 §4.3)。
- 来源标注成 "COA"(Identity V 的另一个赛事/世界赛?)——**需确认它和 IVL 是不是同一批选手、同一赛季的数据**(见 §8)。如果不是同赛事,它只能当弱先验。

### 第 2 层:逐局/选手级数据(`round_metadata`,目标 schema,待采集)

xlsx 里 `round_metadata` 仍是空占位,schema 和你最早上传的一致,计划用**逐局录像/截图 OCR** 采集:

- 对局结构:`game_id, round, survivor_team, hunter_team, escape_num, survivor_score, hunter_score, time, best_player`
- Ban/Pick:`survivor_banned/picked, hunter_banned/picked, map_banned/picked`
- 选手级逐局:`player, role, decode_progress, pallet_strikes, rescues, healing, kiting_time, remaining_ciphers, pallets_destroyed, hit_survivors, terror_shocks, knockdowns`

这是**最细的金矿**(逐局 Ban/Pick、地图、打法风格),但采集成本最高、现在全空。**定位:最后阶段的增强项,不阻塞前面所有工作。** 而且由于第 1.5 层已经提供了选手聚合数据,round 层的紧迫性其实下降了——它的独特价值主要在 **Ban/Pick 和地图**(这是汇总表里没有的)。

### 关于 round 级 OCR 采集的现实评估

既然你打算靠逐局录像/截图 OCR,先把可行性和坑想清楚(这会决定第 2 层值不值得投入):

- **难度分级**(从易到难):
  - 容易:`escape_num`(逃生人数)、`survivor/hunter_score`(每局比分)、地图——这些在结算画面有清晰数字/图标。
  - 中等:`survivor_banned/picked, hunter_picked`(角色头像)——OCR 不行,要做**图标图像分类**(角色头像→角色名),类似你 MVP 聚类那套思路可复用。
  - 困难:`decode_progress, rescues, healing, kiting_time, knockdowns` 等选手级数值——通常只在**赛后详细数据面板**或解说覆盖层里出现,未必每场都有公开画面;OCR 数字易错,需要大量人工校验。
- **建议**:第 2 层**分两批**采集。第一批先只做"容易+中等"字段(比分、逃生数、Ban/Pick、地图),这批就足以支撑一批强特征(见 §4)。选手级数值字段(第二批)等第一版模型跑通、确认确实需要时再投入。
- **复用已有能力**:你的 `clip_label.py`(CLIP 聚类 + OCR)已经能"从图里认人/认名字",角色头像识别可以走同一条技术路线,不用从零搭。

## 4. 特征工程

特征是模型的天花板。按"现在能算"和"等 round 数据后能算"分开列。

### 4.1 仅用第 1 层(比赛级)就能算的特征

这些只依赖 `winner / score / 时间顺序 / mvp`,**现在就能做**:

- **实力评分(最重要)**:给每队维护一个动态评分(Elo / Glicko / TrueSkill,见 §5.1)。每打一场按胜负更新。两队评分差直接映射成胜率。
- **近期状态(form)**:最近 N 场胜率、最近 N 场的平均小局净胜分(从 `game_scores` 解析,如 `5:3` 净 +2)。
- **历史交手(H2H)**:A vs B 历史胜率(对克制关系有用)。
- **小局强度**:不只看 BO 胜负,看每小局比分。`5:3` 和 `7:2` 含金量不同,能更细地反映实力。
- **明星依赖度**:从 `mvp` 列统计——某队的 MVP 是否高度集中在一名选手(如 Gr_Jin、MRC_BaiLu)。明星集中度高 = 上限高但波动大,是个有意思的特征。
- **赛程位置**:常规赛 vs 总决赛(BO 局数不同,强队在长 BO 里更稳)。

### 4.1b 用 `COA_player_total_stats` 算"战队阵容强度"(捷径,需防泄漏)

把选手汇总数据按 `TEAM_player` 前缀聚合回战队,可以构造一批**阵容质量**特征(这是纯比赛级数据给不了的):

- **阵容综合分**:全队选手 `avg_performance_score` 的均值 / 最高值(看整体厚度 vs 单核上限)。
- **监管者强度**:`avg_eliminations / avg_knockdowns / four_kill_rate` 的队内最优值(IVL 里一个强监管能定胜负)。
- **求生位质量**:`escape_rate / avg_kitting / avg_rescues` 的队内均值(拉扯和救人能力)。
- **MVP 火力集中度**:队内 `mvp_num` 的分布(再次量化明星依赖度,和 §4.1 的 mvp 列互相印证)。

> ⚠️ 这些是**赛季汇总值,含未来信息**。只能用在:(a) 路线 B 的赛季级粗特征;(b) 如果将来能拿到**逐场或赛季前半段**的选手汇总,再做成无泄漏的滚动版本。**不要直接塞进单场 walk-forward 模型当输入**,否则回测结果会虚高。

### 4.2 等第 2 层(round 级)数据后能解锁的特征

- **角色池/Ban-Pick 偏好**:某队监管/求生英雄多样性、是否有"必 ban"的克星英雄、首选英雄胜率。
- **地图表现**:分地图的胜率(地图 ban/pick 也是策略信号)。
- **打法风格量化**:平均解码速度(`decode_progress / time`)、救人成功率(`rescues` vs 倒地数)、平均拉刀时长(`kiting_time`)——把"这队是快修流还是拉扯流"变成数字。
- **角色分工稳定性**:选手是否固定位置(`role`),阵容稳定度。

### 4.3 防数据泄漏(务必遵守)

**一条铁律:预测某场比赛时,只能用这场之前发生的信息。**

- 算 Elo / form / H2H 时,严格按时间顺序,只累积到"该场之前"。
- `mvp`、本场 `score`、本场 `winner` 是**结果**,绝对不能进该场的输入特征。
- 实现上用 **walk-forward(滚动)**:按比赛日期排序,逐场预测、再用真实结果更新状态。这同时也是你的验证方式(见 §6)。

## 5. 模型选择

分三档,从简单到复杂,**建议按顺序逐档上**。

### 5.1 基线:评分系统(Elo / Glicko)— 先做这个

- **Elo**:实现 20 行代码,无需训练框架,天然处理时间顺序和增量更新。胜率公式:`P(A win) = 1 / (1 + 10^((R_B - R_A)/400))`。
- 升级版 **Glicko-2 / TrueSkill**:额外建模"评分不确定性",对新队/小样本更稳,推荐。
- **作用**:既是一个特征(评分差),本身也是一个能用的胜率模型,作为后续复杂模型的 baseline。如果复杂模型打不过 Elo,说明特征没用对。

### 5.2 进阶:带特征的概率模型

把 §4 的特征喂给一个输出概率的模型:

- **逻辑回归 / Bradley-Terry 模型**:可解释、适合小样本,Bradley-Terry 专为"两两对战排名"设计,很贴合本场景。
- **梯度提升树(LightGBM / XGBoost)**:能抓非线性和特征交互,但样本量(几百场)偏小,需小心过拟合、配合强正则和交叉验证。
- **建议**:样本量到几百场之前,优先逻辑回归 / Bradley-Terry;GBDT 等第 2 层特征丰富、样本累积更多后再上。

### 5.3 模拟器:蒙特卡洛跑季后赛

有了 `P(A beats B)` 后:

1. **查清 IVL 实际赛制**(常规赛积分规则、季后赛是单败还是双败 bracket、各轮 BO 几局)。这是模拟器正确性的前提,务必先确认。
2. 从当前赛季状态出发,模拟剩余赛程:每场按胜率抛一次"加权硬币"定胜负,推进 bracket 到决出冠军。
3. 重复 N=10000+ 次,统计每队夺冠次数 / N = 夺冠概率。
4. 顺带能输出:进季后赛概率、进决赛概率等。

> BO 内部建议**逐小局模拟**(用单小局胜率),再聚合成 BO 结果,比直接给 BO 胜率更真实(尤其总决赛长 BO)。

## 6. 验证与评估

没有验证的预测等于占卜。这一节和建模同等重要。

### 6.1 单场模型怎么验

- **指标**:Brier score(越低越好)、log loss、校准曲线(预测 70% 胜率的那批比赛,实际是不是真赢了约 70%)。
- **方法**:**walk-forward 回测**。按时间排序,模型只用"过去"预测"下一场",绝不偷看未来。这是体育预测唯一正确的验证方式,普通随机 K 折会泄漏时间信息。
- **对照基线**:始终和两个 dumb baseline 比 —— (a) 永远预测 50/50;(b) 永远预测"Elo 高的队赢"。打不过基线的模型没价值。

### 6.2 夺冠模拟怎么验

- **历史回测**:站在 2025夏/秋赛季**中段**的信息点上,跑模拟,看模型给真实冠军的概率排第几。理想情况真实冠军应在前列(注意:概率模型里"冠军没夺冠概率第一"是正常的,看多赛季整体校准而非单次命中)。
- 因为历史赛季只有 2~3 个,这步更多是"方向性 sanity check",不是严格统计检验。

### 6.3 文档/项目自检清单

- [ ] 所有特征都只用了"比赛之前"的信息?
- [ ] `winner/score/mvp` 没有以任何形式漏进同场输入?
- [ ] 验证用的是时间滚动而非随机折?
- [ ] 模型在回测里能稳定打过 Elo 基线?
- [ ] 模拟器的赛制和 IVL 官方一致?

## 7. 落地路线图(分阶段)

> 原则:**每个阶段结束都有一个能跑、能出概率的东西**,而不是憋大招。

### Phase 0 — 数据整合(最关键、先做,工作量被低估了)

这一步是把 `IVL.xlsx` 的半成品拼成可建模的干净长表,**核心是把 `Sheet1` 的结果回填进 `match_overview` 的赛程骨架**:

- **整合 match_overview ← Sheet1**:`match_overview` 有结构化 ID + 日期但结果空;`Sheet1` 有结果但 ID 是 B 站数字、无日期。两者需要按 `(team_a, team_b, match_score, mvp)` 做匹配回填。难点:同两队一个赛季可能交手多次,匹配会有歧义,可能需要半自动 + 人工核对。**先确认这两张表能否对上**(数量:90 vs 198,Sheet1 还含其它赛季,需先按赛季切分)。
- **队名归一化(必做)**:已发现 `mrc` / `MRC`、`Gr` / `GR`、`FPX.ZQ` 等大小写/写法不一致。建一张映射表统一,否则 Elo 会把同一队当两支。
- **选手名归一化**:已发现 `WBG_nle`(Sheet1)vs `WBG_N1e`(COA 表)——`l` 和 `1` 的 OCR 混淆。聚合选手数据前必须先统一,否则同一人被拆成两条。
- **解析 `game_scores`**:把 `"5:3 | 2:7 | 3:5"` 拆成每小局比分,算净胜分等衍生量。
- **解析结构化 match_id**:从 `2025SW1D1a` 抽出 season / week / day,作为时间排序键(比日期更细)。

产出:`prediction_input/matches_clean.csv`(干净、按时间排好、结果完整的对局长表)+ `prediction_input/players_agg.csv`(归一化后的选手汇总,队名对齐)。

### Phase 1 — Elo 基线 + 单场胜率(最小可用版)

- 实现 Elo/Glicko,按时间滚动更新。
- walk-forward 回测,出 Brier/log loss,和两个 baseline 对比。

## 8. 风险与待确认问题(Open Questions)

1. **`match_overview` 和 `Sheet1` 怎么对齐?** 一个有赛程没结果、一个有结果没日期,且 Sheet1 跨了多个赛季。需确认能否稳定匹配回填,还是得人工补。**这是 Phase 0 能否顺利的关键。**
2. **`COA_player_total_stats` 到底是什么赛事/赛季的数据?** "COA" 看起来不是 IVL(可能是世界赛/COA)。如果选手和赛季对得上 IVL 才能当强特征,否则只能当弱先验。**用之前务必确认来源。**
3. **IVL 季后赛赛制到底是什么?**(单败/双败、各轮 BO 局数、常规赛如何决定种子)——模拟器的正确性完全依赖这个,**优先确认**。
4. **队名/选手名归一化**:已发现 `mrc/MRC`、`Gr/GR`、`WBG_nle/WBG_N1e`(l vs 1)等不一致,需要映射表统一,否则 Elo 会把同一队当两队、选手数据被拆开。
5. **跨赛季评分怎么衔接**:赛季之间转会、版本更新会让实力不连续。建议每赛季对 Elo 做一次"向均值回归"的软重置,而不是直接沿用。
6. **round 级选手数值字段的数据可得性**:这批最难 OCR 且未必每场都有公开画面;由于第 1.5 层汇总表已覆盖大部分选手数值,round 层的独特价值主要剩 **Ban/Pick + 地图**,投入前先权衡。
7. **2026 赛季样本还在累积**:赛季初期预测方差大,夺冠概率会随比赛进行快速收敛,这是正常现象,需在结果里标注"基于截至 X 月 X 日数据"。
